# CONTRIBUTING

Этот файл нужен и для разработчиков, и для агентов, которые будут менять проект.

## Базовые принципы

- сначала понять, относится ли изменение к БД, к файловой системе или к генерации документов
- не считать проект обычным CRUD-приложением
- проверять не только код, но и влияние на реальные файлы, пути и шаблоны
- по возможности не смешивать в одном изменении бизнес-логику, UI и рефакторинг

## Перед началом работы

Нужно понимать:
- какой модуль меняется
- завязан ли он на storage-папки
- есть ли у сценария PDF/DOCX/XLSX генерация
- нужен ли реальный LibreOffice
- есть ли тесты на этот участок

## Локальная разработка

Полезные файлы:
- [README.md](C:\my_projects\doc_helper\README.md)
- [ARCHITECTURE.md](C:\my_projects\doc_helper\ARCHITECTURE.md)
- [`.env.example`](C:\my_projects\doc_helper\.env.example)

Рекомендуется явно задавать:
- `DJANGO_DEBUG`
- `DJANGO_SECRET_KEY`
- `DB_*`
- `DOC_HELPER_BASE_ID_DIR`

## Тесты

Сейчас базовый тестовый контур подготовлен для `projects_app`.

Запуск:

```bash
python manage.py test projects_app --settings=settings.test_settings
```

Если добавляется новая логика в `projects_app`, желательно:
- либо расширять существующие тесты
- либо добавлять новые сценарии в тот же контур

Если меняется `acts_app` или генерация документов, лучше отдельно проверять:
- сборку данных
- создание выходного файла
- ошибки на отсутствующих файлах и путях

## Где сейчас полезнее всего писать тесты

В первую очередь:
- `projects_app`
- `acts_app`
- `passports_app`
- `documents_app`

Особенно полезны тесты на:
- импорт файлов и архивов
- merge-сценарии
- безопасную обработку путей
- выбор актуальных ревизий
- генерацию документов

## Что считать legacy или локально-историческим кодом

На текущий момент:
- `checker_app` не считается активной частью пользовательского контура
- некоторые старые команды и сервисы могли использоваться только локально

Если такой код мешает изменениям:
- сначала проверить, вызывается ли он реально
- потом решать, удалять, изолировать или просто не трогать

## Правила безопасных изменений

- не ломать файловую структуру без явной миграции
- не менять именование storage-папок без понимания всех зависимостей
- аккуратно относиться к архивам и пользовательским путям
- не дублировать похожую логику генерации в нескольких местах, если можно вынести в сервис

## Хороший формат изменений

Хороший change-set для этого проекта:
- один понятный пользовательский эффект
- минимально затронутые модули
- тест или хотя бы проверяемый сценарий
- краткое описание ограничений

## Что особенно помогает агентам

Если добавляешь новый важный сценарий, полезно сразу обновить:
- `README.md`, если меняется способ запуска или общая картина
- `ARCHITECTURE.md`, если меняются связи модулей
- этот файл, если появляются новые правила работы с кодом
